# Web Demo 구현 계획

## 1. 목적과 범위

이 문서는 `web_demo/`의 단일 시나리오 웹 데모를 구현, 검수, 배포하기
위한 작업 계획이다. 데모는 서울 수서권 집결지에서 철도 접근 및 환승을
거쳐 평택지제역/평택 지원 권역으로 이동하는 하나의 공개자료 기반
시나리오를 설명한다.

데모의 성격은 다음으로 고정한다.

- 공개자료와 저장소 내 샘플 결과를 사용하는 비운영 연구 데모
- 버스 단독과 철도-버스 복합 수송을 비교하는 의사결정지원 시각화
- 재난, 교통망 장애, 공공부문 비상수송 계획 검토를 위한 설명 도구
- 최종 연구 승인, 실제 작전계획, 실제 이동 지시, 실시간 예측 시스템이 아님

UI, 지도, 수치, 보고서 문구는 모두 `final_study_ready=false` 상태와
형식적 승인 0/12 상태를 전제로 작성한다. 어떤 화면도 "최적 경로",
"실제 소요시간 보장", "운영 가능", "승인 완료"처럼 해석될 수 있는 표현을
사용하지 않는다.

## 2. 고정 시나리오

데모는 여러 지역을 동시에 다루지 않고 하나의 시나리오만 다룬다.

- 집결 권역: 서울 수서/SRT 접근권 주변의 가상 집결 지점
- 1차 도로 이동: 집결 지점에서 수서 철도 접근 지점까지 셔틀 이동
- 철도 구간: 수서권 철도 접근 지점에서 평택지제역 권역까지 이동
- 말단 도로 이동: 평택지제역 권역에서 평택 지원 권역까지 이동
- 비교 정책: `bus_only`와 `multimodal`
- 장애 관점: 도로 차단, 용량 감소, 혼잡, 집결 지연, 차량 가용성 제약,
  환승 지연을 설명 가능한 수준으로 시각화

좌표와 라벨은 공개자료 또는 명시된 예시 좌표로만 사용한다. 실제 보안시설,
실제 부대, 실제 작전 출발지/목적지처럼 보일 수 있는 위치명은 피하고,
"수서권 집결지", "수서 철도 접근점", "평택지제 환승권",
"평택 지원 권역"처럼 일반화된 라벨을 사용한다.

## 3. 필수 산출물

`web_demo/` 안에서 관리할 산출물은 다음과 같다.

- 시나리오 정의: 지도 라벨, 경유점, 설명 문구, 정책 비교 범위
- 지도 데이터: 수서권, 평택지제권, 평택 지원 권역 표시 좌표와 경로선
- 샘플 텔레메트리: 데모용 요약 지표, 시간 흐름, 이벤트 로그, 정책별 KPI
- UI 화면: 지도, 시나리오 패널, 정책 비교, 지표 표, 증거/한계 패널
- 검증 기록: lint/build 결과, 브라우저 확인 결과, 스크린샷 캡처 경로
- 선택 배포 기록: Vercel 배포 URL, inspect 결과, 배포 시점의 커밋/빌드 상태
- 최종 보고서용 문구 초안: 스크린샷 이후 확정되는 설명 문단과 캡션

## 4. 작업 순서와 의존성

작업은 아래 순서를 지켜야 한다. 하위 단계가 완료되지 않으면 후속 단계의
문구나 산출물을 확정하지 않는다.

1. 시나리오 freeze
   - 수서권 집결, 수서 철도 접근, 평택지제 환승, 평택 지원 권역이라는
     단일 시나리오를 고정한다.
   - 정책 비교 범위와 표현 금지어를 확정한다.
   - 산출물: `scenario_freeze.md` 또는 동등한 PR/작업 로그.

2. 지도 좌표/라벨 정리
   - freeze된 시나리오를 기준으로 좌표와 라벨을 갱신한다.
   - 좌표 출처, 예시 여부, 일반화 처리 여부를 기록한다.
   - 산출물: 지도 데이터 파일, 좌표 출처 메모, UI 라벨 목록.

3. 샘플 텔레메트리 갱신
   - 지도 라벨과 동일한 시나리오명을 사용해 샘플 결과를 맞춘다.
   - 실제 연구 승인값처럼 보이지 않도록 `sample`, `demo`, `scaffold`
     성격을 명시한다.
   - 산출물: `public/data/`의 샘플 CSV/JSON/YAML, 데이터 사전.

4. UI 구현 및 로컬 검증
   - 지도, 비교 지표, 이벤트 타임라인, 한계/증거 패널을 구현한다.
   - `npm run lint`, `npm run build`를 통과시킨다.
   - 로컬 브라우저에서 지도 타일, 라벨, 반응형 레이아웃, 콘솔 오류를 확인한다.
   - 산출물: 구현 코드, 로컬 검증 로그, 브라우저 확인 메모.

5. Vercel 배포
   - 사용자가 요청한 경우에만 Vercel 배포를 수행한다.
   - 배포 전 `npm run lint`와 `npm run build`가 통과해야 한다.
   - 산출물: 배포 URL, `vercel inspect` 요약, 배포 커밋/브랜치 정보.

6. 스크린샷 캡처
   - 배포가 요청된 경우 배포 URL에서 캡처한다.
   - 배포가 요청되지 않은 경우 로컬 preview 또는 dev 서버에서 캡처한다.
   - 데스크톱과 모바일 폭을 모두 확인한다.
   - 산출물: 주요 화면 스크린샷, 캡처 URL/시각/viewport 메모.

7. 최종 보고서 문구 작성
   - 스크린샷에 실제로 보이는 화면을 기준으로 문구를 작성한다.
   - 데모가 비운영, 비최종, 공개자료 기반 의사결정지원 도구라는 경계를
     반복해서 명시한다.
   - 산출물: 보고서 삽입 문단, 그림 캡션, 한계 문구.

### 4.1 보고서 작업과의 교차 의존성

`web_demo/plan.md`와 `국방AI_활용_아이디어_경연대회/plan.md`는 같은
시나리오를 공유하되, 산출물 확정 순서는 다르다. 웹 데모는 보고서의 시각
증거를 만들고, 보고서는 그 증거를 해석하는 downstream 산출물이다.

공통 선후 관계는 다음과 같이 고정한다.

1. 시나리오 동결: 두 계획이 동일한 서울/수서-평택지제-평택 지원 권역
   시나리오명을 사용한다.
2. 공개 근거 정리: 보고서의 출처 행렬이 지도 라벨과 캡션의 근거를 제공한다.
3. 웹 데모 구현: 지도, 라벨, 샘플 KPI, 비작전 주의 문구를 먼저 반영한다.
4. 로컬 검증과 배포: lint/build/browser 확인 이후에만 Vercel URL을 확정한다.
5. 스크린샷 캡처: 확정 URL 또는 검증된 로컬 preview에서만 캡처한다.
6. 보고서 문구 확정: 캡처 화면에 실제로 보이는 기능과 문구만 보고서에 쓴다.
7. 주장 안전성 검토: 보고서와 데모가 서로 다른 시나리오나 과장 표현을
   만들지 않았는지 마지막에 교차 점검한다.

### 4.2 Sub-Agent Dependency DAG

웹 데모 작업은 다음 방향성 그래프로 관리한다.

```text
Scenario Lead
  -> Map/Data Agent
  -> Telemetry Agent
  -> Frontend Agent
  -> Deployment Agent
  -> Screenshot Agent
  -> Report Agent
  -> QA/Boundary Reviewer

Scenario Lead
  -> Telemetry Agent

Map/Data Agent
  -> Frontend Agent
  -> Screenshot Agent

Telemetry Agent
  -> Frontend Agent
  -> Report Agent

Deployment Agent
  -> Screenshot Agent
  -> Report Agent
```

Critical path는 `Scenario Lead -> Map/Data Agent -> Frontend Agent ->
Deployment Agent -> Screenshot Agent -> Report Agent -> QA/Boundary Reviewer`
이다. 이 경로가 끝나기 전에는 최종 보고서 문단, 캡션, 제출용 화면 설명을
완료로 표시하지 않는다.

병렬 가능한 작업은 제한적으로 허용한다.

- Scenario Lead가 시나리오명, 금지 표현, 권역 라벨을 고정한 뒤에는
  Map/Data Agent와 Telemetry Agent가 병렬로 작업할 수 있다.
- Frontend Agent가 첫 렌더링을 마친 뒤에는 Deployment Agent가 배포 준비를,
  QA/Boundary Reviewer가 UI 문구 사전 검토를 병렬로 진행할 수 있다.
- Screenshot Agent는 배포 URL 또는 검증된 로컬 preview가 확정되기 전에는
  최종 캡처를 시작하지 않는다.

동기화 gate는 다음 네 지점이다.

1. Scenario freeze gate: 시나리오명, 권역 라벨, 금지 표현 확정.
2. Implementation gate: 지도와 telemetry가 같은 시나리오를 가리키고
   lint/build가 통과.
3. Deployment gate: Vercel URL 또는 검증된 로컬 preview가 실제로 로드됨.
4. Evidence gate: 스크린샷, URL, 화면 문구가 보고서 문단과 일치함.

## 5. gpt-5.5 high 하위 에이전트 실행 모델

하위 작업은 `gpt-5.5 high` 수준의 코드/검토 에이전트를 가정해 나눈다.
각 에이전트는 자기 산출물과 검증 증거를 남기고, 다음 에이전트가 그
산출물을 입력으로 사용한다.

| 역할 | 주요 책임 | 선행 의존성 | 핸드오프 산출물 | 수용 기준 |
| --- | --- | --- | --- | --- |
| Scenario Lead | 단일 시나리오 freeze, 금지 표현, 메시지 경계 확정 | 없음 | 시나리오 freeze 메모, 라벨 정책 | 수서-평택지제-평택 지원 권역으로 범위가 단일화됨 |
| Map/Data Agent | 좌표, 지도 라벨, 경로선, 출처 메모 정리 | Scenario Lead | 지도 데이터, 좌표/라벨 표 | 실제 작전지처럼 보이는 라벨이 없고 UI 좌표가 일관됨 |
| Telemetry Agent | 샘플 KPI, 이벤트 로그, 정책별 비교 데이터 정리 | Scenario Lead, Map/Data Agent | 샘플 telemetry 파일, 데이터 사전 | 모든 값이 데모 샘플로 표기되고 지도 라벨과 충돌하지 않음 |
| Frontend Agent | React/Vite UI 구현, 반응형 화면, 증거/한계 패널 | Map/Data Agent, Telemetry Agent | 구현 코드, 로컬 실행 메모 | lint/build 통과, 콘솔 오류 없음, 모바일에서 텍스트 겹침 없음 |
| Deployment Agent | 요청 시 Vercel 배포와 inspect 확인 | Frontend Agent | 배포 URL, inspect 요약 | 배포 빌드 성공, 공개 URL에서 화면 로드 |
| Screenshot Agent | 데스크톱/모바일 스크린샷 캡처 | Frontend Agent, Deployment Agent 또는 로컬 preview | 스크린샷 파일, viewport 기록 | 캡처가 최신 화면과 일치하고 핵심 패널이 보임 |
| Report Agent | 최종 보고서 문구와 캡션 작성 | Screenshot Agent | 보고서 문단, 캡션, 한계 문구 | 스크린샷에 없는 기능을 주장하지 않음 |
| QA/Boundary Reviewer | 전체 증거와 문구 경계 검수 | 모든 에이전트 | 검수 체크리스트 | 운영계획, 최종승인, 실제예측으로 오해될 표현이 없음 |

## 6. 하위 에이전트별 체크리스트

### Scenario Lead

- 시나리오가 하나만 존재하는지 확인한다.
- 지도와 텔레메트리에서 같은 지명 체계를 쓰도록 라벨 목록을 고정한다.
- "public-data", "non-operational", "non-final", "decision-support" 경계를
  한국어와 영어 설명 모두에 반영한다.
- 실제 기관, 실제 작전명, 민감 시설을 암시하는 표현을 제거한다.

### Map/Data Agent

- Leaflet 지도에서 수서권과 평택지제/평택 지원 권역이 한 화면 흐름으로
  이해되는지 확인한다.
- 경로선은 개념 경로로 표시하고, 실제 운행 지시처럼 보이는 turn-by-turn
  안내는 만들지 않는다.
- 좌표 파일 또는 코드 주석에 예시/공개자료 기반 여부를 기록한다.
- 라벨은 일반화된 권역명만 사용한다.

### Telemetry Agent

- 기존 `public/data/config.yaml`과 `public/data/phase1_results.csv` 사용
  여부를 확인하고, 필요하면 시나리오명과 설명 필드를 갱신한다.
- 샘플 데이터는 실제 성능 보증이나 최종 연구 결과로 표시하지 않는다.
- KPI는 비교 설명에 필요한 최소 집합으로 유지한다.
- 결측값, 임의값, scaffold 값은 UI와 데이터 사전에 명확히 표시한다.

### Frontend Agent

- 첫 화면에서 바로 지도와 정책 비교가 보이도록 구성한다.
- 데모 목적 설명은 별도 마케팅 페이지가 아니라 분석 화면 안의 한계/증거
  패널로 제공한다.
- 버튼, 탭, 표, 지도 범례는 기존 BlueprintJS/React/Tailwind 구성을 따른다.
- 모바일 폭에서 지도, 표, 패널 텍스트가 겹치지 않는지 확인한다.
- UI 문구는 연구 프로토타입 경계를 벗어나지 않는다.

### Deployment Agent

- 배포는 사용자가 명시적으로 요청한 경우에만 진행한다.
- 배포 전 로컬 검증 명령을 다시 실행한다.
- 배포 URL, inspect 결과, 빌드 환경을 기록한다.
- 배포 결과가 실패하면 스크린샷과 보고서 문구 작성을 중단하고 실패 원인을
  먼저 정리한다.

### Screenshot Agent

- 배포가 있으면 배포 URL을 기준으로 캡처한다.
- 배포가 없으면 `npm run preview` 또는 `npm run dev`의 로컬 URL을 기준으로
  캡처한다.
- 최소 데스크톱 1장, 모바일 1장을 남긴다.
- 캡처 전에 콘솔 오류, 지도 로드, 데이터 패널 렌더링을 확인한다.

### Report Agent

- 캡처된 화면에 실제로 있는 기능만 설명한다.
- "본 데모는 공개자료 기반 비운영 의사결정지원 예시"라는 문장을 포함한다.
- `final_study_ready=false`와 형식적 승인 미완료 상태를 흐리지 않는다.
- 그림 캡션은 "개념 시각화", "샘플 결과", "비최종 검토용"의 성격을 드러낸다.

## 7. 수용 기준

웹 데모 작업은 다음 조건을 모두 만족해야 완료로 본다.

- 단일 시나리오가 수서권 집결 및 철도 접근에서 평택지제/평택 지원 권역으로
  이어지는 흐름으로 고정되어 있다.
- 지도 라벨, 샘플 텔레메트리, UI 문구가 같은 시나리오명을 사용한다.
- UI 어디에도 실제 작전계획, 실제 운송 지시, 확정 예측, 최종 승인으로
  읽힐 표현이 없다.
- `npm run lint`가 통과한다.
- `npm run build`가 통과한다.
- 브라우저에서 지도, 비교 패널, 샘플 데이터, 한계/증거 문구가 렌더링된다.
- 데스크톱과 모바일에서 핵심 텍스트가 겹치지 않는다.
- Vercel 배포가 요청된 경우 배포 URL이 정상 로드되고 inspect 결과가 기록된다.
- 스크린샷 캡처 이후에만 최종 보고서 문구와 캡션을 확정한다.

## 8. 검증 명령

`web_demo/`에서 다음 명령을 사용한다.

```powershell
npm run lint
npm run build
```

로컬 브라우저 확인이 필요하면 다음 중 하나를 사용한다.

```powershell
npm run dev
npm run preview
```

Vercel 배포는 사용자가 요청한 경우에만 실행한다.

```powershell
vercel deploy
vercel inspect <deployment-url>
```

배포 전후로 확인할 항목은 다음과 같다.

- 빌드 실패 또는 TypeScript 오류 없음
- 브라우저 콘솔의 치명적 오류 없음
- 지도 타일과 경로선 렌더링
- 수서권, 수서 철도 접근점, 평택지제 환승권, 평택 지원 권역 라벨 표시
- 정책 비교 패널의 `bus_only`와 `multimodal` 값 표시
- 한계/증거 패널의 비운영, 비최종, 공개자료 기반 문구 표시
- 모바일 viewport에서 텍스트, 버튼, 표, 지도 범례가 겹치지 않음

## 9. 보고서 문구 작성 원칙

보고서나 발표자료에는 다음 취지의 문구를 사용한다.

> 본 웹 데모는 수서권 집결 및 철도 접근, 평택지제 환승, 평택 지원 권역
> 이동을 하나의 공개자료 기반 예시로 구성한 비운영 의사결정지원
> 시각화이다. 표시된 경로와 수치는 최종 승인된 운송계획이나 실제
> 소요시간 예측이 아니라, 도로 장애와 환승 불확실성 아래에서 정책
> 대안을 비교하는 연구 프로토타입의 샘플 결과이다.

스크린샷 캡션은 다음 요소를 포함한다.

- 단일 시나리오 범위: 수서권-평택지제-평택 지원 권역
- 비교 대상: 버스 단독과 철도-버스 복합 수송
- 증거 경계: 공개자료 기반 샘플, 비운영, 비최종
- 목적: 최종 지시가 아니라 의사결정지원과 회복탄력성 평가

## 10. 중단 조건

다음 상황이 발생하면 후속 단계로 넘어가지 않는다.

- 시나리오 freeze 없이 좌표나 텔레메트리를 먼저 확정하려는 경우
- 지도 라벨과 샘플 데이터의 지역명이 서로 다른 경우
- 샘플 수치가 실제 확정 성능처럼 표현되는 경우
- `npm run lint` 또는 `npm run build`가 실패한 경우
- 배포 실패 상태에서 스크린샷이나 보고서 문구를 확정하려는 경우
- 스크린샷에 보이지 않는 기능을 최종 보고서가 주장하는 경우

이 중단 조건은 작업 속도보다 우선한다. 데모의 핵심 품질은 화려한 화면보다
시나리오 일관성, 증거 경계, 검증 가능한 산출물 순서에 있다.
